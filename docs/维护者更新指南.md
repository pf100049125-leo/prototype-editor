# 维护者更新指南（GitHub 网页操作）

适用于原项目所有者，以及已获得原仓库写权限的协作者。你可以直接在原仓库创建分支，无需 Fork。

- 原项目仓库：[pf100049125-leo/prototype-editor](https://github.com/pf100049125-leo/prototype-editor)
- 初始基线：[v1.0.0](https://github.com/pf100049125-leo/prototype-editor/tree/v1.0.0)
- 外部使用者请阅读：[外部贡献者更新指南](外部贡献者更新指南.md)

## 先了解三个名称

| 名称 | 作用 |
| --- | --- |
| `main` | 当前稳定源码；平时从这里创建新分支 |
| `feature/server-tabs` 等分支 | 保存某项功能的修改，合并前不会改变 main |
| `v1.0.0` 标签 | 固定的初始基线；日常更新不移动这个标签 |

操作流程：**创建分支 → 修改或上传源码 → 等待检查并试用 → 创建 PR → 合并到 main**。

新建分支、编辑文件、上传源码和申请合并，都可以在 GitHub 网页完成，不要求使用 PowerShell。GitHub 负责保存源码和构建 EXE，具体功能仍需要你或开发者修改实现。

## 1．打开原仓库

1. 登录拥有仓库权限的 GitHub 账号。
2. 打开[原项目仓库](https://github.com/pf100049125-leo/prototype-editor)。
3. 点击上方 **Code**，进入文件列表。
4. 确认网址仍是 `pf100049125-leo/prototype-editor`。

## 2．从最新 main 新建分支

1. 点击文件列表上方显示 **main** 的版本下拉框。如果当前是其他版本，先在 **Branches** 中选择 **main**。
2. 再次打开下拉框，在 **Branches** 页签的搜索框输入新名称，例如 `feature/server-tabs`。
3. 点击 **Create branch … from main**。
4. 创建后，确认版本按钮变成 **feature/server-tabs**。

名称可以按修改内容填写：

| 修改内容 | 分支示例 |
| --- | --- |
| 新增 Server 页签功能 | `feature/server-tabs` |
| 修复图片导出 | `fix/export-image` |
| 修改 IO Alarm 页面 | `feature/io-alarm` |

如果下拉框中没有创建选项，可以点击 **View all branches → New branch**，输入名称，来源选择 **main**，再创建。若看不到写入入口，先确认登录账号及仓库权限。

每次新功能通常从最新 main 开始。同一个尚未完成的功能，继续使用原修改分支。

## 3．在分支中修改或上传源码

先确认当前分支是 **feature/server-tabs**。

### 方法 A：直接在网页编辑

1. 打开要修改的源码文件。
2. 点击铅笔按钮 **Edit this file**。
3. 修改内容，点击 **Commit changes**。
4. 填写说明，例如“修复 Server 页签切换问题”。
5. 选择提交到当前分支，再确认 **Commit changes**。

### 方法 B：上传已经修改好的源码

1. 在当前分支进入文件对应的文件夹。
2. 点击 **Add file → Upload files**。窄屏下入口可能收在更多菜单中。
3. 上传文件，等待文件列表显示完成。
4. 填写提交说明，选择提交到当前分支，点击 **Commit changes**。

文件位置必须对应：

| 本地修改 | 网页上传位置 |
| --- | --- |
| `src/editor.js` | 进入 `src` 后上传 `editor.js` |
| `app/main.cjs` | 进入 `app` 后上传 `main.cjs` |
| 整个 `src` 文件夹 | 在仓库根目录拖入 `src` 文件夹，并核对上传路径 |

上传前后都核对路径，避免把 `src/editor.js` 放成根目录的 `editor.js`。上传同路径文件会更新该文件，但不会自动删除已经不用的旧文件；确需删除源码时，在修改分支打开对应文件，使用文件菜单中的 **Delete file** 并提交。

上传的是开发源码，不能只上传 EXE 或 ZIP。不要上传 `node_modules`、`.qa`、`.dev-profile`、`dist` 或生成的 `app/index.html`；网页上传也要自己核对这些内容。网页每个文件最大 25 MiB，一次最多上传 100 个文件。

如果本地源码已经改好了，可以直接上传改过的文件。创建网页分支不会自动同步电脑上的修改。

## 4．检查结果并下载试用 EXE

提交后，仓库的 CI 会检查源码、运行测试并构建 Windows 试用 EXE。

1. 点击仓库上方 **Actions**。
2. 打开对应提交的 **CI** 记录，确认显示的分支是 **feature/server-tabs**。
3. 等待运行完成。绿色对勾表示成功；红叉表示有步骤失败。
4. 成功后，在运行详情下方找到 **Artifacts**。
5. 下载名称以 **windows-preview-** 开头的压缩包。
6. 解压，运行里面的便携 EXE，验证相关页面和交互。

需要登录 GitHub 才能下载 Actions 附件。试用包通常保留 7 天；过期后可以重新运行工作流。

若没有运行记录，进入 **Actions → CI → Run workflow**，选择修改分支并运行。若失败，打开失败步骤查看日志，修复后继续提交到同一个分支。需要他人排查时，提供运行链接及错误信息。

## 5．创建合并申请（Pull Request，简称 PR）

试用符合要求后：

1. 点击上方 **Pull requests → New pull request**，或分支页面出现的 **Compare & pull request**。
2. 将 **base** 设置为 `main`。
3. 将 **compare** 设置为 `feature/server-tabs`。
4. 查看文件差异，点击 **Create pull request**。
5. 填写标题、修改内容和验证方法，再确认创建。

示例：

- 标题：增加 Server 页签功能
- 修改内容：支持新增、删除和调整顺序，各页签内容独立。
- 验证方法：已下载试用 EXE，验证新增、切换、删除及保存后重开。

如果提示没有差异，确认文件确实提交到了该分支，而不只是创建了一个分支。

## 6．检查通过后合并到 main

1. 打开这条 PR。
2. 在 **Files changed** 核对文件和实际改动。
3. 等待 **Windows checks and build** 检查通过，并处理未解决的讨论。
4. 点击 **Merge pull request**（或可用的合并方式），再点击 **Confirm merge**。
5. 回到 **Code**，切换到 **main**，确认修改已进入稳定源码。

main 已配置分支保护，因此更新按 PR 流程进行。若提示分支落后或存在冲突，先更新修改分支并解决冲突，再等待检查通过。

## 7．继续修改与下一次更新

- 同一功能还没有合并：继续向原分支提交，新提交会自动加入已打开的 PR。
- 功能已经合并，又开始新的修改：从最新 main 新建另一个分支，重复以上流程。
- 合并后的功能分支可以按需要保留或删除；固定基线标签 v1.0.0 继续保留。

## 如果修改是在 EXE 编辑器里完成的

网页提交源码与 EXE 内的页面编辑是两件事。EXE 中点击页面的 Save，不会把修改上传到 GitHub。

1. 在 EXE 使用 **文件 → 保存工程**，导出工程 JSON。
2. 按[开发指南](开发指南.md#工程导入和回退)把工程导入开发源码，核对页面与交互。当前导入需本地运行脚本，可交给开发者协助完成。
3. 把导入后变动的源码提交到修改分支，继续执行上面的检查和 PR 流程。

直接把工程 JSON 上传到仓库，不会自动替换内置原型；只上传 EXE 或导出的单个 HTML，也不能代替源码更新。

## 分支更新与正式发布的区别

创建分支和合并 PR 不会自动修改软件版本号，也不会自动更新已有的 v1.0.0 下载包。

准备正式发布时，先按 [CONTRIBUTING.md](../CONTRIBUTING.md#发布一个新版本)同步软件版本、记录改动，并将对应源码通过 PR 合并到 main，再建立与软件版本一致的新标签，例如 v1.0.1。标签应指向通过检查的 main 提交；已有基线标签保持原位。
