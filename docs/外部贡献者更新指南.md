# 外部贡献者更新指南（基于 v1.0.0，GitHub 网页操作）

适用于没有原仓库写权限，希望基于 **v1.0.0 基线**改进工具并提交给项目维护者的使用者。

- 原项目：[pf100049125-leo/prototype-editor](https://github.com/pf100049125-leo/prototype-editor)
- 固定基线：[v1.0.0](https://github.com/pf100049125-leo/prototype-editor/tree/v1.0.0)
- 如果你是项目所有者或已获得写权限，请阅读[维护者更新指南](维护者更新指南.md)。

操作流程：**Fork 到自己的账号 → 从 v1.0.0 创建分支 → 修改并提交源码 → 下载试用包 → 向原项目提交 PR**。

以上仓库操作均可在 GitHub 网页完成，不要求使用 PowerShell。具体功能需要你或开发者修改源码实现；在 EXE 内编辑原型工程的情况见文末说明。

## 先了解仓库、分支和标签

| 名称 | 含义 |
| --- | --- |
| 原仓库 | `pf100049125-leo/prototype-editor`，由项目维护者管理 |
| Fork 副本 | `你的账号/prototype-editor`，你可以在其中创建分支和上传修改 |
| 修改分支 | 例如 `feature/server-tabs`，保存你的一项改动 |
| `v1.0.0` 标签 | 固定的初始版本；本说明要求以它作为修改起点 |
| PR | Pull Request，向维护者申请把你的修改合并到原项目 |

Fork 提供可写的仓库副本。后续的新建分支和提交都在你的副本中进行，原仓库只有在维护者接受合并后才会改变。

## 1．Fork 到自己的 GitHub 账号

1. 登录你自己的 GitHub 账号。
2. 打开[原项目仓库](https://github.com/pf100049125-leo/prototype-editor)。
3. 点击右上角 **Fork**。
4. 在 **Owner** 选择自己的账号，仓库名称保留 `prototype-editor`。
5. 点击 **Create fork**。
6. 创建后确认网址变成 `https://github.com/你的账号/prototype-editor`。

如果以前已经 Fork 过，直接进入已有副本，不需要重复创建。

## 2．选择 v1.0.0 并创建自己的修改分支

必须先选中基线，再创建分支，避免误从后来更新的 main 开始。

1. 在你的 Fork 仓库点击 **Code**。
2. 点击文件列表上方显示 **main** 的版本下拉框。
3. 在弹出的窗口切换到 **Tags**，点击 **v1.0.0**。
4. 确认文件列表上方显示 **v1.0.0**。
5. 再次打开这个版本下拉框，切换到 **Branches** 页签。
6. 在 **Filter branches** 搜索框输入一个未使用的分支名，例如 `feature/server-tabs`。
7. 点击 **Create branch … from v1.0.0**。确认按钮写的是 **from v1.0.0**，再点击创建。
8. 创建后，确认版本按钮变成 **feature/server-tabs**。

注意第 5 步：停留在 Tags 中只会搜索标签，需要切回 Branches 才能创建分支。

如果找不到 v1.0.0，先确认原项目的[基线页面](https://github.com/pf100049125-leo/prototype-editor/tree/v1.0.0)能打开，再确认访问的是这个项目的 Fork 副本；把自己的仓库链接提供给维护者协助核对，不要用其他版本冒充基线。

| 修改内容 | 分支名称示例 |
| --- | --- |
| 新增 Server 页签 | `feature/server-tabs` |
| 修复图片导出 | `fix/export-image` |
| 调整 IO Alarm | `feature/io-alarm` |

## 3．编辑源码或上传修改文件

先确认当前处于 **feature/server-tabs** 分支。

### 在网页直接编辑

1. 打开需要修改的文件。
2. 点击铅笔按钮 **Edit this file**。
3. 修改代码，点击 **Commit changes**。
4. 填写简短说明，例如“修复 Server 页签切换问题”。
5. 选择提交到当前分支，再确认提交。

### 上传本地已经修改好的源码

1. 进入文件对应的文件夹。
2. 点击 **Add file → Upload files**。
3. 上传修改文件，核对路径。
4. 填写提交说明，选择当前修改分支，点击 **Commit changes**。

例如：

| 修改文件 | 上传方式 |
| --- | --- |
| `src/editor.js` | 在仓库进入 `src` 后上传 `editor.js` |
| `app/main.cjs` | 在仓库进入 `app` 后上传 `main.cjs` |
| 整个 `src` 文件夹 | 在仓库根目录拖入 `src`，并核对内部文件路径 |

上传文件夹时保留原结构。上传同路径文件会更新内容，但不会自动删除旧文件；确需删除时，在修改分支打开文件并从文件菜单选择 **Delete file**，然后提交。

不要上传依赖和缓存目录（`node_modules`、`.qa`、`.dev-profile`）、`dist`、EXE、源码 ZIP 或生成的 `app/index.html`。网页上传每个文件最大 25 MiB，一次最多 100 个文件。

修改源码的位置和开发方法见原项目 main 上的[开发指南](https://github.com/pf100049125-leo/prototype-editor/blob/main/docs/开发指南.md)。

## 4．启用检查并下载试用 EXE

Fork 中的 Actions 可能默认未启用。

1. 在你的 Fork 仓库点击 **Actions**。
2. 如果提示工作流未启用，按页面提示启用。
3. 提交源码后，打开对应提交的 **CI** 记录，核对分支。
4. 若没有运行记录，进入 **Actions → CI → Run workflow**，选择 **feature/server-tabs**，启动运行。
5. 等待绿色对勾，打开运行详情。
6. 在下方 **Artifacts** 下载名称以 **windows-preview-** 开头的压缩包。
7. 解压并运行 EXE，验证修改的页面和交互。

如果 Actions 要求额外账户验证或显示运行限制，按 GitHub 提示处理；也可以先创建 PR，由维护者在原仓库批准相应检查。

下载 Actions 附件需要登录 GitHub。试用包保留 7 天；过期后重新运行 CI。若出现红叉，查看失败步骤的日志并修复后继续提交。测试涉及原型基线，主动修改页面结构或默认值时，也需要开发者核对相关测试预期，不能仅为通过检查而删除测试。

## 5．向原项目提交 PR

修改完成并试用通过后：

1. 进入你的 Fork，切换到 **feature/server-tabs**。
2. 点击 **Contribute → Open pull request**。也可以在原仓库的 **Pull requests → New pull request → compare across forks** 选择来源。
3. 核对下表中的接收与来源。
4. 查看差异，填写标题和说明，点击 **Create pull request**。

| 选项 | 应选择的内容 |
| --- | --- |
| 接收仓库 base repository | `pf100049125-leo/prototype-editor` |
| 接收分支 base | `main` |
| 来源仓库 head repository | `你的账号/prototype-editor` |
| 来源分支 compare | `feature/server-tabs` |

说明中写清楚：

- 以 v1.0.0 基线开始，修改了哪些页面或功能。
- 如何操作才能看到修改效果。
- 已验证的内容，以及是否存在尚未解决的问题。

首次贡献或来自 Fork 的 PR 检查，可能需要维护者批准运行。创建 PR 是提出合并申请，维护者接受后改动才会进入原项目。若原项目 main 已有后续更新，PR 还可能需要更新分支、解决冲突并重新检查。

## 6．继续修正同一项修改

如果 PR 尚未合并，继续在你的 **feature/server-tabs** 分支编辑和提交即可。新提交会自动加入同一个 PR，不需要重复创建。

PR 合并后，若要做另一项改动，先与维护者确定起点：

- 需要严格从原始基线独立开发：重新从 v1.0.0 创建一个新名称的分支。
- 需要接着最新正式功能开发：先在 Fork 使用 **Sync fork** 同步原项目 main，再从更新后的 main 创建新分支。它属于基于最新版本开发，与严格从 v1.0.0 开始不同。

同步涉及冲突时先核对差异，不要使用丢弃修改的选项覆盖尚未提交或尚需保留的工作。

## 如果你只在 EXE 中修改了页面

EXE 内的页面编辑不会自动进入 GitHub 分支。

1. 在 EXE 使用 **文件 → 保存工程**，导出工程 JSON。页面中的 Save 不能代替“保存工程”。
2. 按[开发指南的工程导入步骤](https://github.com/pf100049125-leo/prototype-editor/blob/main/docs/开发指南.md#工程导入和回退)，在本地把 JSON 导入开发源码，并检查页面与交互。当前这个导入步骤需要运行本地脚本，可请开发者协助。
3. 将导入后变动的源码提交到自己的修改分支，再创建 PR。

仅上传 JSON、EXE 或导出的单个 HTML，不会自动更新工具内置原型。

## 关于正式版本

分支名称不是软件版本号。分支提交会产生试用包，但不会自动改变原项目的 v1.0.0 Release。

向原项目贡献时，正式版本号和发版由维护者统一安排。基线标签 v1.0.0 保持原位。你自己的 Fork 中的分支也可以继续保留，供后续开发。
